# 会员订单创建 40K/80K 容量测试验收报告设计

## 1. 目标与读者

本设计用于生成一份面向技术团队的 Markdown 验收与交接报告。报告同时承担四项职责：

1. 对 `8 × 5K = 40K` 与 `8 × 10K = 80K` 两轮正式边界测试给出可复核结论。
2. 用统一表格比较八个区段的吞吐、墙钟耗时和延迟分位数。
3. 复盘测试期间出现的业务逻辑、测试基础设施、运行环境和报告聚合问题。
4. 提供全量启动、从 `E-AR` 续跑、从 `H-P1` 续跑、两秒心跳监控及 RabbitMQ 只读检查命令，便于其他工程师本地接手。

最终报告写入：

```text
docs/handoffs/2026-08-28-membership-order-create-40k-80k-capacity-acceptance-report.md
```

## 2. 方案选择

评估过三种组织方式：

- 单一综合报告：正文给结论、性能和故障复盘，附录给命令与接管手册。
- 拆分报告：40K、80K、故障复盘和运行手册分别成文。
- 时间线日志：按数日测试过程逐次记录。

采用单一综合报告。它能让验收结论与原始证据保持在同一上下文中，又能通过附录隔离长 PowerShell 命令，避免正文被操作细节淹没。拆分报告会增加结论漂移风险；纯时间线不利于直接回答“最终是否通过”。

## 3. 事实来源与证据优先级

报告只使用本地已经存在的正式产物、数据库核验结果和项目文档，不重新执行压测，也不以截图中的主观观察替代文件证据。

证据优先级如下：

1. 区段级正式结果、`verdict.json`、HTTP 报告、`scenario-orders.csv` 和数据库最终扫描。
2. `run-state.json`、`heartbeat.json`、stdout/stderr 与进程状态，用于解释编排阶段和停止原因。
3. RabbitMQ 队列快照、Redis 工作集合和 PostgreSQL 状态分布，用于解释收敛与残留。
4. 现有 ADR、交接文档、测试报告和 Git 变更记录，用于复盘根因与修复设计。
5. 截图只作为人工观察补充，不作为唯一验收依据。

正式结果来源固定为：

- 40K 前三段：`membership-order-create-auto-20260827-102027-performance-40k`
- 40K `E-AR`：`membership-order-create-resume-ear-5kx8-20260827-135706`
- 40K 后四段：`membership-order-create-resume-hp1-5kx4-20260827-174807`
- 80K 前三段：`membership-order-create-capacity-80k-20260828-121713`
- 80K `E-AR`：`membership-order-create-capacity-80k-20260828-160053`
- 80K 后四段：`membership-order-create-capacity-80k-20260828-164946`

## 4. 核心结论口径

报告必须同时给出三层结论：

1. 功能与数据一致性：八个正式区段是否全部完成，订单与回调是否一一对应，是否存在缺失或重复。
2. 性能合同：每段 QPS 是否不低于 900，墙钟时间是否低于对应规模上限。
3. 黄金目标：是否达到 `<5 秒且 >1,000 QPS` 的历史黄金目标；未达到时不能把“合同 PASS”写成“完全复现黄金基线”。

40K 与 80K 的八个区段级裁决均为 `PASS`。80K 最终数据库事实为 80,000 个订单、80,000 条回调、80,000 个回调订单，缺失回调为 0，重复回调为 0；订单和回调的裁决分布均为 `APPLIED=49,963`、`REFUND_REQUIRED=30,037`。

两个最后续跑 Run 的顶层原始 verdict 均为 `FAIL`，失败码为 `MILLISECOND_BOUNDARY_SUITE_FAILURE`，来源阶段为 `FORMAL_GOLDEN_REPORT`。这是报告器只接受“单个 Canary 区段”或“同一 Run 内完整八段”，而最后续跑 Run 只包含四段造成的聚合门禁假阴性。报告必须写成：

```text
八个业务正式区段与最终数据验收 PASS；顶层聚合报告因四段续跑形态产生假阴性 FAIL。
```

禁止把该顶层 FAIL 误写成 RabbitMQ、Redis、数据库或业务状态机失败，也禁止隐去这个原始事实。

## 5. 报告结构

最终报告按以下顺序组织：

1. 执行摘要与最终验收结论。
2. 测试目标、范围、八区段含义与固定环境合同。
3. 40K 结果总表。
4. 80K 结果总表。
5. 40K/80K 横向对比与扩容结论。
6. 最终数据库、Redis、RabbitMQ 和日志一致性核验。
7. 问题时间线与根因、修复、验证、遗留风险。
8. 运行与续跑手册。
9. 心跳、进程和基础设施诊断手册。
10. 证据索引与准确性边界。

性能表至少包含：区段、请求数、成功数、墙钟秒数、QPS、P50、P95、P99、功能裁决和黄金复现裁决。

横向比较至少包含：订单数、正式墙钟总和、有效 QPS、平均区段 QPS、最低/最高区段 QPS、数据完整性和顶层聚合状态。报告应明确：订单数翻倍后，正式墙钟总和约增加 94.4%，有效 QPS 约提高 2.9%。

## 6. 问题复盘分类

问题不按情绪或截图顺序堆叠，而按以下分类复盘，每项统一写“现象、根因、修复/处置、验证、是否影响最终验收”。

### 6.1 业务状态机问题

- 取消与支付发起竞态导致 Redis 与 PostgreSQL 状态分叉。
- `REJECTED` 回调删除 provider-result，导致后续查询变为 `UNKNOWN` 并永久停在 `CLOSING`。
- 回调订单级和第三方流水级幂等边界。
- 终态回调的 `APPLIED/REFUND_REQUIRED` 裁决与退款工作收敛。

### 6.2 性能与容量问题

- Redis 写入从 `192×2/384` 调整为 `64×6/384`，降低重 Pipeline 的队头阻塞和尾延迟。
- Callback 与 OrderPersist 独立调度器及单轮 5,000 条处理能力。
- 最近已支付订单查询使用部分索引，避免泛化预编译计划无法证明 `status = 2`。
- Hikari、PostgreSQL `max_connections`、Tomcat 和 RabbitMQ Channel/消费者容量的边界。

### 6.3 测试脚本与门禁问题

- JMeter `paidAt` 时间精度导致合法性前提被测试数据自身破坏。
- 合法延迟消息与区段边界竞争曾被旧门禁误判。
- 80K Token 页码白名单仍停留在 40K 的 `0–79`，导致 `H-P1` 从第 80 页开始时停止；修复为 `0–159` 后重打 JAR。
- 分段续跑只包含四段，顶层黄金报告器仍要求一段或八段，产生汇总假阴性。
- `ExpectedFormalSegmentCount`、`StartGroupCode` 与 authoritative scenario 清单的职责边界。

### 6.4 运行环境与恢复问题

- 调度器被外部强制结束时无法执行正常 `STOPPED` 收尾，旧心跳文件不再更新。
- 旧应用消费者退出导致 RabbitMQ 到期消息无人消费；重新启动唯一应用后，两个业务队列恢复为 48 个消费者并完成收敛。
- RabbitMQ `list_queues` 是只读查询；`purge_queue` 是破坏性应急操作，不能作为常规启动步骤。
- Windows 宿主或 Job Object 回收进程树与 PostgreSQL/调度器正常停止的区别。
- Navicat 默认 `LIMIT 50000` 导致把 80,000 条 callback 误看成 50,000 条。

用户口述中的“etcd”没有对应本轮正式证据。最终报告不虚构 etcd 故障；若上下文实际指 Redis，则统一按 Redis 记录。

## 7. 命令与运行手册设计

命令附录包含四张可直接复制的 PowerShell 命令卡：

1. 从 `E-P1` 启动完整八段。
2. 已有前三段证据时，从 `E-AR` 续跑剩余五段。
3. 已有前四段证据时，从 `H-P1` 续跑剩余四段。
4. 每两秒读取 `current-80k-run-id.txt`、`run-state.json` 与 `heartbeat.json` 的监控命令。

所有命令必须：

- 使用真实 PowerShell 语法，不包含 Markdown 转义产生的 `\_`、`$\_` 或多余反斜杠。
- 在启动前检查所需 scenario CSV 和 PostgreSQL 门禁证据存在。
- 生成新 Run ID，不覆盖历史证据。
- 明确区分 `MasterRunId` 与当前子 `RunId`。
- 归档正式日志后再启动，并将 stdout/stderr 写入当前 Run 的 launcher 文件。
- 只在 `run-state.json` 显示 `RUNNING` 且 `applicationPid` 存在时报告启动成功。

诊断附录另外提供 RabbitMQ 只读队列查询、PID/端口核验和日志读取命令。破坏性清理不放入标准流程；如确需记录，必须放入单独的“应急操作”小节并标明精确目标、不可恢复性和执行前提。

## 8. 准确性与安全边界

- 不宣称本轮重新执行了任何命令或压测。
- 不把截图中的旧心跳延迟当作新恢复应用的心跳。
- 不把 `consumers=48` 等同于旧调度器恢复；它只证明当前应用的 RabbitMQ 消费者已注册。
- 不把 RabbitMQ 队列无积压单独视为端到端成功，必须结合数据库终态和回调事实。
- 不把 Redis Pipeline 描述为事务、Exactly Once 或强一致。
- 不把 RabbitMQ、PostgreSQL 或 Redis 的历史残留清理写成每轮必须手工执行的固定步骤。
- 不包含生产 Secret、密码、Token 或无法脱敏的身份数据。

## 9. 自检与完成标准

最终报告生成后执行以下只读自检：

1. 检查 Markdown 中不存在 `TBD`、`TODO` 或未替换占位符。
2. 核对 40K 与 80K 各八段请求总数分别为 40,000 和 80,000。
3. 重新计算墙钟总和、有效 QPS、平均/最低/最高区段 QPS 与百分比变化。
4. 检查所有本地相对链接目标存在。
5. 检查 PowerShell 代码块不存在错误转义，并用 PowerShell Parser 做语法解析；只解析，不执行启动、清理或压测。
6. 检查报告同时保留“区段级 PASS”和“顶层聚合假阴性 FAIL”两项事实。
7. 检查 Git diff 只包含本次新增的规格、计划和最终报告，不改动用户现有业务文件。

## 10. 交付范围

本次只新增文档，不修改 Java、YAML、PowerShell 业务脚本，不重新打包，不启动应用，不清理 Redis/RabbitMQ/PostgreSQL，也不重新执行 40K/80K。最终交付物是一份可审计验收报告，以及用于生成该报告的设计和写作计划。
