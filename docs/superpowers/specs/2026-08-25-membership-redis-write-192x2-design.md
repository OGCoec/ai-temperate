# 会员订单 Redis 写入 192×2/384 设计

> **状态：已被取代。** 自 2026-08-26 起，生产与正式压测采用
> [`64×6/384` 设计](2026-08-26-membership-redis-write-64x6-design.md)；本文仅保留为历史基线和环境变量回滚说明，不得作为新运行的配置证据。

## 已批准边界

- 单个 Pipeline 最多包含 192 个独立订单写入。
- 固定使用 2 个 lane；每个 lane 只有一个串行 Worker，因此系统最多同时执行 2 个 Pipeline 批次。
- 全局公平许可固定为 384，约束排队中与执行中的 Redis 逻辑订单写入总数。
- HTTP 创建并发仍为 256，本次不通过扩大 HTTP 请求量制造吞吐假象。

## 并发与顺序不变量

订单继续按订单 ID 稳定散列到固定 lane。同一订单的后续写入不会跨 lane，并由 lane 内 FIFO 保证前序写入完成后才执行后序写入。两个 lane 可以并行执行，但每个 lane 不会同时提交第二个 Pipeline，因此在途 Pipeline 批次上限天然为 2。

全局 `Semaphore(384, true)` 在写入进入 lane 队列前领取许可，并在结果完成或受控失败后释放。任意时刻 `inflight + availablePermits = 384`，不允许无界提交 Lettuce 命令。

## 配置与证据合同

Java 默认值、Spring YAML、应用启动脚本、Suite、子编排器、运行采样器和正式证据清单必须同时记录 `192/2/384`。运行探针发现任意一个值漂移时立即判定配置合同失败。

## 失败语义

Pipeline 执行失败、队列提交超时或关闭期间未完成的写入继续精确完成为受控失败；不提前返回 HTTP，也不改变 PostgreSQL、Redis Lua 或 RabbitMQ 的可靠性合同。
