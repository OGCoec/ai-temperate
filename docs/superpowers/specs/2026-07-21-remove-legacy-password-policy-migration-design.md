# 移除历史密码策略迁移设计

## 背景与目标

项目不存在需要兼容的历史用户数据，当前用户的密码已符合强度要求。因此，删除仅为“无法从旧密码哈希反推明文强度”而引入的 006 迁移及其持久化状态，避免无意义地把登录用户标记为必须重置密码。

目标是让密码强度规则只在用户提供明文密码的写入边界执行：注册、修改密码和找回密码完成时必须校验；既有密码登录和验证码登录不再依赖数据库中的强度等级或策略版本。

## 方案选择

1. 推荐：彻底删除 006 迁移、两个策略元数据列及全部读写和登录拦截逻辑。
   这与“没有历史用户需要迁移”的事实一致，数据模型仅保存登录凭据所必需的信息。
2. 保留两列但移除登录拦截。
   会遗留没有业务用途的状态、约束和维护成本，不采用。
3. 保留迁移并把现有用户回填为当前版本。
   仍然把不可验证的历史结论写入数据库，且没有兼容对象，不采用。

## 数据与行为边界

`userloginidentity` 表继续保存邮箱、手机号、密码哈希和 `password_version`；它不是本次删除目标。

删除的只有 `password_strength_level`、`password_policy_version`、两者的检查约束，以及 006 正向和回滚脚本。初始建表 SQL 同步移除这些字段，保证新库不会再创建它们。

密码强度策略保留，用于注册和密码重置的明文校验。密码登录继续执行密码哈希比对；验证码登录继续按账号状态签发会话，两者均不再因历史强度元数据拒绝用户。

## 受影响边界

- model：身份实体与认证上下文移除两个策略字段和构造参数。
- mapper：结果映射、查询列、插入列及改密更新语句不再读写策略字段；改密 Mapper 只接收 ID 与新密码哈希。
- service：注册和重置仍调用 `validateForWrite`，但不持久化评估结果；登录和验证码登录移除 `requiresReset` 分支。
- database：删除 006、其回滚与检查 SQL；更新 001 和认证上下文文档。
- tests：同步移除仅验证已删除字段或“必须重置”的断言，保留对注册、改密和密码强度校验的覆盖。

## 验收标准

- 仓库中不再存在 006 脚本、密码策略列、相关约束、Mapper 参数或登录重置判断。
- 新密码仍必须在注册和重置时达到当前强度策略要求。
- 用户密码登录与验证码登录不再读取或依赖已删除的策略持久化状态。
- 不删除 `userloginidentity`、`password_hash` 或 `password_version`。

## 验证边界

本项目当前处于第一阶段。只交付代码与测试源文件，不运行测试、编译、打包、数据库迁移或任何外部服务连接。第二阶段需由用户明确批准具体命令和测试环境后再进行。
