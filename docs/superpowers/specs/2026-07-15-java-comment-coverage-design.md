# Java 中文注释全量覆盖设计

## 目标

为仓库内全部非自动生成 Java 源文件补充准确的中文用途说明，并仅在确实存在复杂机制的实现中补充原理注释，使维护者无需先阅读全部实现即可理解文件职责、关键不变量与协作边界。

## 覆盖范围

- 覆盖 `src/main/java` 下全部生产 Java 源文件。
- 覆盖 `src/test/java` 下全部测试 Java 源文件。
- 排除构建产物、自动生成代码和非 Java 文件。
- 每个文件的主要顶级类型（`class`、`interface`、`enum` 或 `record`）必须具备中文 JavaDoc；第一句明确该文件是来做什么的。

## 注释分层

### 第一层：全部文件的用途说明

主要顶级类型的 JavaDoc 必须说明：

- 文件承担的业务或技术职责。
- 它解决的问题或提供的能力。
- 主要协作对象、输入输出或明确不负责的边界。

简单 DTO、VO、枚举、异常、Mapper 和测试类也需要用途说明，但保持简洁，禁止用大量无价值注释填充文件。

### 第二层：按实际机制补充原理说明

只有文件实际包含下列机制时，才在类级 JavaDoc、公开方法 JavaDoc 或紧邻代码块的中文 `//` 注释中说明原因、顺序或不变量：

- 复杂业务编排、状态流转、失败补偿或跨服务协作。
- 事务边界、提交后动作、回滚处理或缓存一致性。
- Redis/Lua、锁、CAS、重试、限流、幂等键、并发控制或原子操作。
- Token、密码、CSRF、授权、输入验证、防重放或敏感数据保护。
- HTTP/DTO/缓存/数据库/消息等边界转换、编码、规范化或校验。

注释必须解释“为什么这样做”和失败影响，禁止逐行复述代码；不得出现明文 Token、密码、验证码、完整手机号、完整邮箱或安全绕过细节。

## 实施方式

1. 按模块分批处理 `common`、`mapper`、`model`、`service`、`web` 及其测试代码。
2. 每批先为全部文件补主要类型的用途 JavaDoc。
3. 再针对实际含复杂机制的文件补原理注释；不得为不存在的并发、事务或幂等逻辑虚构说明。
4. 每批只做注释改动，不重构业务逻辑、不修改运行行为。
5. 使用静态扫描检查用途 JavaDoc 覆盖与复杂机制文件的注释位置；本项目第一阶段不运行编译、测试或外部服务验证。

## 验收标准

- 所有纳入范围的 Java 文件都有主要顶级类型的中文用途 JavaDoc。
- 含复杂业务、事务、并发、幂等、安全或边界转换的实现，具有与实际代码一致的原理说明。
- 简单类型的注释简洁、准确，不重复类名或显而易见语法。
- 注释不泄露敏感信息，也不改变任何业务行为。
- Code Review 可以依据 `AGENTS.md` 的 Java 中文注释规范逐项检查。
