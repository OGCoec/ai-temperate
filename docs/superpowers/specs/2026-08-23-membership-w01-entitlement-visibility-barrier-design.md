# W01 权益可见性屏障设计

## 问题

W01 用 30 个并发线程循环使用 16 个固定账号。每账号 semaphore 能防止同时创建两笔活动订单，但订单 Redis 快照先进入 `PAID` 时，PostgreSQL 权益事务和用户资料缓存失效可能尚未完成。后一个案例会在旧套餐仍可购买时冻结请求体；前一个案例随后把账号升级为该套餐，后一个请求因此被正确拒绝为 `MEMBERSHIP_TRANSITION_REJECTED`。

## 选择

在每账号 semaphore 内增加权益可见性屏障。`PAID/APPLIED` 案例取得最终订单状态后，继续通过正式 `GET /api/user/membership-plan-offers` 轮询，直到刚购买的目标套餐不再出现在合法报价中，再释放账号给下一案例。下一案例随后重新读取报价并选择当前合法的更高套餐。原有订单创建 409 有界重试只处理 PostgreSQL 活动订单释放的短暂窗口。

该方案不直接读写数据库，不增加测试后门，不放宽单活动订单或只允许向上升级的产品约束，也不执行会污染并发线程的全局 FREE 重置。

## 超时和失败

权益可见性最长等待 60 秒，每 250 毫秒读取一次正式报价。超过期限仍能购买刚支付的套餐时，案例失败并保留证据；不得静默选择其他套餐。报价接口非 200 立即失败。

## 验证

先用静态契约测试证明脚本缺少权益屏障，再实现最小轮询；契约通过后，清理本轮精确测试数据并完整重跑 W01。只有完整 W01 PASS 才继续 W02。

## 同根因的后续波次保护

W02 的 Marker 矩阵同样循环账号，因此使用相同的创建屏障和权益可见性屏障。波次编排器在每次调用 JMeter 前只读查询 16 个固定账号的当前会员等级，并把 Token CSV 按等级从低到高稳定重排，使 51 次预期 APPLIED 均匀消耗 64 个合法升级台阶；该排序不修改会员数据。W03-B 的第二订单使用第 5 个保留账号，不再扫描并复用四个主线程中的第一账号。
