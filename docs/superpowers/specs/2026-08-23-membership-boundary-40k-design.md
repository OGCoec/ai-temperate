# 会员支付 40,000 账号边界测试缩容设计

## 目标

将现有 400,000 账号、8×50,000 的本机 JMeter 会员支付边界测试缩减为 40,000 账号、8×5,000，同时把两条会员 RabbitMQ 队列的消费者固定为每队列 48 个。测试继续验证订单、回调与权益状态机的微秒级业务时间边界。

## 固定运行合同

- 固定账号范围为 `70000000000000000～70000000000039999`，总数 40,000。
- 八个区段依次为 `E-P1`、`E-PR`、`E-A1`、`E-AR`、`H-P1`、`H-PR`、`H-A1`、`H-AR`，每段 5,000。
- 每段 GO、PLUS、PRO、MAX 各 1,250；TEAM 负向探针按原比例缩减为每段 25。
- 毫秒偏移循环仍为 500，不改变 `-1ms`、`-1000～-2ms`、`+1ms`、`0～+998ms` 的边界定义。
- JMeter `CreationConcurrency` 与 `HttpConcurrency` 均保持 4,096。
- 两条会员 RabbitMQ 队列各使用 48 个消费者，单消费者 prefetch 保持 20。
- 正式预检保持 120 秒，区段间稳定窗口保持 60 秒。
- PostgreSQL 和证据 CSV 中的业务时间继续统一输出 UTC 六位小数微秒。
- 本机 HTTP `ConnectException` 只允许使用原始幂等键进行最多三次有界随机退避；HTTP 状态错误和业务错误不重试，实际尝试次数写入证据。

## 数据缩容与清理

先保留失败运行的审计证据，再清理本轮订单、回调和 Redis 会员支付测试状态。随后按逻辑关联顺序删除序号 `40,000～399,999` 的固定测试账号额度、资料和身份，只保留前 40,000 个账号。删除前后必须核对明确范围和影响行数，禁止影响固定前缀以外的数据。

保留的 40,000 个账号全部恢复为 FREE：完整 FREE 额度、`quota_period_started_at=NULL`、`membership_expires_at=NULL`。正式运行前必须确认订单和回调均为 0，Redis 会员支付状态为空，RabbitMQ Ready、Unacked 和 DLQ 均为 0。

## 验证与失败处理

代码合同测试必须覆盖 40,000 总量、8×5,000、每套餐 1,250、每段 25 个 TEAM 探针、48 个消费者、prefetch 20 以及两个 4,096 并发上限。完成打包和单实例重启后，先验证数据库、Redis、RabbitMQ 和端口基线，再用新 Run ID 执行正式 JMeter 套件。

任一区段失败时保留该次证据，停止进入下一段，定位并修复后以新的 Run ID 从干净 40,000 FREE 基线重试。
