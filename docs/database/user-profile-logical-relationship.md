# user_profile 与 userloginidentity 逻辑关系

## 关系定义

user_profile.login_identity_id 逻辑关联 userloginidentity.id，业务上是一对一关系。
user_profile 中的唯一约束为该关联字段提供 B-tree 索引，并阻止同一登录身份重复创建资料。
数据库不负责强制关联完整性，所有补偿控制由应用事务、影响行数校验、巡检和恢复流程共同承担。

## 写入验证

创建用户资料前，Service 必须在同一个 PostgreSQL 本地事务中确认目标
userloginidentity 已存在，然后调用批量边界明确的 Mapper 写入资料。
本次单条注册流程必须校验身份、资料状态和会员额度插入的影响行数都等于 1；任一结果异常时回滚整个本地事务。
不得由 Controller、脚本或其他上层调用绕过 Service 直接写入关联数据。

## 删除顺序

删除用户时必须在同一个 PostgreSQL 本地事务中先删除依赖方 user_membership_quota 和 user_profile，校验影响行数后再删除
主记录 userloginidentity。如果业务选择保留资料用于审计，必须先显式转入独立归档结构，
不得留下仍指向已删除登录身份的在线记录。事务提交后再由上层执行缓存失效。

## 孤儿数据检查

巡检 SQL 位于 sql/checks/user_profile_orphans.sql。该 SQL 使用关联字段上的既有唯一 B-tree
索引识别缺少登录身份的资料。生产环境应该由受控的离线巡检任务定期执行并记录结果数量，
不得通过无边界业务接口向客户端返回完整巡检结果。

## 恢复方式

发现孤儿记录后应先停止相关写入入口并保存待处置记录快照。若备份或权威审计记录能够证明
登录身份应当存在，则先恢复身份记录，再复查关联；若无法证明主记录合法存在，则在人工确认后
删除或归档孤儿资料。所有修复必须放在 PostgreSQL 本地事务中，并校验实际影响行数。
修复完成后重新执行孤儿数据检查，结果为零才可结束处置。

## 接受风险

项目明确接受没有数据库级关联强制机制带来的完整性窗口。应用层存在性校验不能宣称绝对关系完整性：
绕过应用的人工 SQL、缺陷脚本或异常恢复都可能产生孤儿数据。该风险通过统一 Service 写入口、
本地事务、删除顺序、影响行数校验、定期巡检和可审计恢复流程降低，但不能被完全消除。
