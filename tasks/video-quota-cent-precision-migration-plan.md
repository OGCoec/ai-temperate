# 视频供应商成本额度单位修正计划

## 目标

统一把账户额度解释为“美元金额，保留两位小数”：

```text
quota_balance_minor = 美分整数
5000       -> 50.00
200000     -> 2000.00
0.84 美元  -> 扣减 84 个 minor
```

当前视频 ticks 转换在得到美分数量后又乘了一次 `100`，导致 `$0.84` 被转换为 `8400` 个 minor（显示为 `84.00`）。目标是改为 `84` 个 minor（显示为 `0.84`）。套餐余额、套餐上限和数据库现有缩放比例保持不变。

## 不变量与换算规则

- xAI 成本单位保持 `1 USD = 10,000,000,000 ticks`。
- 账户余额单位固定为美分整数：`1 USD = 100 quota_minor`。
- `100,000,000 ticks = 0.01 USD = 1 quota_minor`。
- 预扣和最终结算必须使用同一个整数向上取整规则。
- 6 秒、P720 的示例：`6 × 1,400,000,000 = 8,400,000,000 ticks`，最终预扣 `84`，余额 `5000` 变为 `4916`，页面显示从 `50.00` 变为 `49.16`。
- 不修改 `quota_balance_minor` 的数据库缩放比例，不修改 FREE/PLUS 等套餐值，不增加销售倍率。
- `estimated_provider_cost_ticks` 仍保存供应商 ticks 快照；它与 `reserved_quota_minor` 不能混用。

## 任务列表

### 阶段一：成本换算边界

#### 任务 1：修正 ticks 到账户 minor 的转换

**涉及：** `AiConversationProviderCostQuotaCalculator`。

**改动：**

- 将 `COST_TICKS_PER_QUOTA` 改名为明确表达美分的常量，例如 `COST_TICKS_PER_QUOTA_MINOR`。
- `actualQuotaMinor(long)` 和视频预扣使用 `ceil(ticks / 100_000_000)`，删除 `* MINOR_UNITS_PER_QUOTA`。
- 保留负数校验、整数溢出保护和向上取整。
- `reservedQuotaMinor(short)` 的图片输出预扣策略先保持原有保守值 `100 minor/张`，避免无意改变图片预扣政策；图片最终实际成本使用同一美元到美分转换规则。

**验收：**

- `8400000000 -> 84`。
- `1400000000 -> 14`。
- `1 -> 1`，`100000001 -> 2`。
- `0 -> 0`，负数仍然拒绝。

#### 任务 2：同步预扣和最终结算

**涉及：** `AiConversationBillingServiceImpl`、`AiConversationSettlementServiceImpl`。

**改动：**

- 视频预扣、成功结算、失败退款和差额补扣全部使用修正后的 `quota_minor` 单位。
- 确认视频请求不会再叠加普通 Token 计费。
- 保持余额行锁和事务边界不变。
- 对图片 provider-cost 结算明确记录其“按美元 ticks 转美分”的规则；图片预扣仍可按输出数量做保守预留，完成后退还差额。

**验收：**

- 预扣 `$0.84` 为 `84`。
- 实际 `$0.80` 退还 `4`；实际 `$0.90` 补扣 `6`。
- 预扣失败时余额、usage 和 detail 均不改变。

### 检查点一：单位一致性

- [ ] 视频预扣、结算、退款、补扣使用同一单位。
- [ ] 套餐配置和现有余额不变。
- [ ] API 的 `quotaBalanceMinor` 仍是字符串美分整数，`quotaBalance` 仍按两位小数展示。

### 阶段二：快照、历史数据和文档

#### 任务 3：更新快照字段说明和数据库文档

**涉及：** `ai_model_usage_detail` 相关 Entity、Mapper XML、SQL 注释、运行文档。

**改动：**

- 明确 `reserved_quota_minor`、`charged_quota_minor`、`settlement_delta_minor` 的单位是美分整数。
- 明确 `estimated_provider_cost_ticks` 是 xAI ticks，不能直接当作额度。
- 不修改历史行的数值或重新解释历史单位；历史行继续按创建时的单位保留。

#### 任务 4：历史错误扣费审计

**改动：**

- 提供只读审计 SQL：按 provider ticks 重新计算应扣美分，与历史 `charged_quota_minor` 比较差额。
- 只有确认历史视频已按旧错误规则成功扣费后，才通过现有退款/人工对账事务补回差额。
- `AI_QUOTA_INSUFFICIENT` 且未建立 usage 的请求不产生退款记录。

**验收：**

- 能区分旧规则记录、新规则记录、待对账记录和无成本记录。
- 不直接批量覆盖历史账单。

### 阶段三：测试与交付

#### 任务 5：补充单元和业务结算测试

**必须覆盖：**

- 6 秒 P720：`8400 -> 84`。
- P480/P720/P1080 每秒价格：`8/14/25 minor`（xAI 1.5 配置）。
- 1、2、6、15 秒边界。
- 1 tick、整分、非整分的向上取整。
- 预扣不足、成功结算、退款、补扣和余额不足对账。
- 图片保守预扣与实际成本退款。
- 普通 Token 计费结果不受视频修正影响。

#### 任务 6：更新契约测试和说明

- 更新 `AiConversationProviderCostQuotaCalculatorTest`、视频 Billing 测试及结算测试中的期望值。
- 更新 API/前端契约说明，避免把 raw minor 误称为完整额度。
- 不新增环境变量；价格 ticks 仍由主业务的现有配置读取。

### 检查点二：发布前

- [ ] 代码、SQL、Mapper、API、前端显示和历史审计单位一致。
- [ ] 用户余额不被迁移脚本改变。
- [ ] 旧记录不会被新算法静默重算。
- [ ] 用户批准第二阶段后再执行测试、编译和数据库验证。

## 明确禁止的改法

- 不把视频价格 ticks 除以 `100`，那会真实少收 100 倍。
- 不修改套餐 `5000/200000` 来掩盖换算错误。
- 不只修改预扣而不修改最终结算，否则会出现预扣、退款和实际扣费单位不一致。
- 不直接重写历史 `charged_quota_minor`。

## 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 只改预扣不改结算 | 成功后仍按旧规则扣费 | 预扣与结算共用一个转换方法 |
| 修改共享常量影响图片/普通对话 | 旧功能收费变化 | 先区分 provider-cost 与 token 路径并补测试 |
| 页面余额缓存滞后 | 用户误以为余额被扣光 | 以数据库行锁余额为准，提交后失效缓存 |
| 历史账单混用单位 | 对账错误 | 保留历史值并增加单位版本/审计 SQL |

## 当前结论

按你最后确认的目标，应该把当前视频成本转换从 `8400` 改为 `84`，而不是改套餐。这个目标保留现有套餐的 `50.00/2000.00` 语义，修正的是 provider ticks 到账户美分整数的第二次乘 `100`。
